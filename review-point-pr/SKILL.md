# Review point PR

レビューで気づいた点を、コメントではなくコミットで示すためのPRを作る。
レビュイーはコミット単位で取り込むかどうかを選べる。

## 完成形

タイトル:

```
Review point for #<元PR番号>: <対象>の改善案
```

本文:

```markdown
Review point for <元PRのURL>: <対象>の改善案

| コミット | 指摘 | 変更内容 |
| --- | --- | --- |
| a1b2c3d | DDL が途中で失敗すると、テーブルが残って再実行できない | 失敗したら `down()` で片付ける |
| e4f5a6b | テーブル名が定数で、読みにくい | 文字列で直接書く |
```

## 手順

### 1. 形式を確かめる

ユーザーが参考PRのURLを渡したら、その形式に合わせる。

```bash
gh pr view <番号> -R <owner/repo> --json title,body
```

渡されなければ、上の「完成形」を使う。

### 2. ベースと元PRを決める

ベースは、レビュー対象PRのhead ブランチにする。develop や main にはしない。

- レビュー用ブランチ名が `<元ブランチ>__<名前>` なら、`<元ブランチ>` がベース。
- 決められないときはユーザーに聞く。

元PRを探す:

```bash
git fetch -q origin
gh pr list --head <ベースブランチ> --json number,title,url
```

### 3. 対象のコミットを集める

```bash
git log --oneline --no-merges origin/<ベースブランチ>..HEAD
```

- push 済みか確かめる（`git status -sb`）。未 push なら、push してよいかユーザーに聞く。
- 未コミットの変更はPRに入らない。残っていたら、最後の報告で触れる。

### 4. コミットごとに「指摘」と「変更内容」を書く

各コミットの差分を読む。コミットメッセージだけで書かない。

```bash
git show --stat <sha>
git show <sha>
```

書き方:

| 列 | 書くこと | 例 |
| --- | --- | --- |
| コミット | 短い SHA（7桁） | `a1b2c3d` |
| 指摘 | 元のコードの何が問題か。レビュイーの立場で読んで分かる言葉にする | `author_id` に FK が無く、著者が消えると画面が壊れる |
| 変更内容 | どう直したか。1〜2文で | `authors` へ `restrict` の FK を張る |

- 1つの指摘を複数のコミットで直したときは、2行目以降の「指摘」を「同上」にする。
- 指摘は断定しすぎない。好みの範囲なら「〜読みにくそうでした」のように書く。
- 表の順は、コミットの古い順。

### 5. PRを作る

本文はファイルに書いてから渡す。シェルのエスケープで表が崩れるのを防ぐ。

```bash
gh pr create --draft \
  -R <owner/repo> \
  --base <ベースブランチ> \
  --head <レビュー用ブランチ> \
  --title "Review point for #<元PR番号>: <対象>の改善案" \
  --body-file <本文ファイル>
```

- `--draft` は、ユーザーが draft を頼んだときに付ける。
- リポジトリのルールで本文の末尾に付ける行（attribution など）があれば、表のあとに付ける。

### 6. 報告する

- 作ったPRのURL
- ベースとhead
- 「指摘」の列は差分から推測して書いたこと。意図と違えば直してほしいこと
- PRに入っていない未コミットの変更があれば、そのファイル
